## Findings
| # | Severity | Location | Evidence | Required correction |
|---|---|---|---|---|
| F1 | minor | `AbilityService.luau` `reject()` (`player:SetAttribute("AbilityRejections", …)`) | Every rejected request writes a replicated attribute on the `Player` object. Player attributes replicate to **every** client, so (a) each player's rejection count leaks to all clients (low-value, but it is telemetry about exploit attempts), and (b) a spamming client turns each spam packet into a server-side property write that gets replicated to all players. Rate limiting does not stop this, because rejections are exactly the spam path. The stated reason ("may load a separate copy") is a test convenience, not a gameplay need. | Keep the counter server-side only (it is already in `state.rejections` and `getRejectionCount`). If tests need an Instance-visible value, write it only in Studio (`RunService:IsStudio()`), or throttle it (for example, at most once per `WarnIntervalSeconds`), or put it on a server-only object such as a `ServerStorage` value. |
| F2 | minor | `AbilityService.luau` `onRequest`, `canUse` call | `registration.canUse(player)` runs outside the `pcall`. A future faction `canUse` that errors (for example, indexing missing data while the player loads) raises inside `OnServerEvent`, which breaks the AC rule "rejected and don't error". No `canUse` is registered today, so this is latent. `canActivate` and the commit come after it without a yield, so a yielding `canUse` does not open a cooldown race. | Wrap `canUse` in `pcall` and treat an error or a non-`true` result as `reject(..., "not_eligible")`. Document that `canUse` must not yield. |
| F3 | minor | `Dash.luau` (`velocity.MaxForce = math.huge`), and the character check in `AbilityService.onRequest` | Unbounded planar force on the root. If the humanoid is seated (`SeatPart`), the root is welded into the seat's assembly, so Dash drives the whole vehicle or seat assembly with infinite force. Against other unanchored assemblies, an infinite actuator force can fling them. There is no check for `Humanoid.SeatPart`, `PlatformStand`, or the `Dead`/`Physics` states beyond `Health > 0`. Cleanup on death or removal is fine: `task.delay` → `Destroy()` on an already-destroyed instance does not error, and the constraint dies with the character. | Use a finite force, sized for example as `root.AssemblyMass * k` or a config constant, and reject (or no-op) when `humanoid.SeatPart ~= nil`. Add a config field rather than a magic number. |
| F4 | minor | `tests/luau/AbilityRules.spec.luau` | The AC asks for NaN/nil **args**. The spec tests `nil` ids and a NaN clock, but not a NaN number id (`0/0`), a boolean, a Vector3/Instance id, or a NaN `extraArgCount`. Specs also cover only the pure rules. The service-level ordering (rate before validate, cooldown committed before the handler, rejected spam counts toward the window) is verified only by the one manual playtest. | Add `validateRequest(0/0, 0, KNOWN) == "bad_type"` and one more non-string type. Optionally add a short comment or test asserting that `checkRate` counts rejected calls, since the service relies on that. |
| F5 | nit | `AbilityService.luau` `getState` + `PlayerRemoving` | `PlayerRemoving` clears `states[player]`. A remote event that is already queued and handled after removal would recreate the entry through `getState`, leaving a small per-player leak. Unlikely and bounded. | In `onRequest`, return early if `player.Parent ~= Players`, or use `states[player]` without lazy creation after removal. |
| F6 | nit | [[TEST-20261010-03]] / task note | The playtest `build` says "working tree, pre-commit" rather than a commit hash. The touch button was not tried even in Studio's device emulator, which needs no TASK-0009 harness. The "visible to other clients" AC rests on indirect evidence. | When repeating the 2-client check (after TASK-0009, or manually through Studio Test → 2 players), record the commit hash, and also press the touch button in the device emulator. Tick AC2 only after that. |

**Reviewed and accepted (no finding):**
- **Remote arguments:** `onRequest(player, abilityId, ...)` with `select("#", ...)` correctly rejects any extra payload. Trailing-nil counting does not matter here, since `"Dash", nil` is harmless either way. Ids are type- and length-checked before indexing plain, metatable-free registry and config tables.
- **Rate limit:** the sliding window counts rejected requests, and memory is capped at `max + 1` timestamps per player. Keeping only the newest `max + 1` timestamps never changes a decision. State is keyed by `Player`, which bounds it by player count.
- **Cooldown:** the check and the commit happen with no yield between them, before the handler. A handler error still uses up the cooldown, which is fine.
- **Security:** the client sends only an id. Direction comes from the server's view of `root.CFrame` and force from config, and there are no targets. An exploiter who owns their own character's physics can move anyway. That is outside this task.
- **Scope deviations:** `src/server/Abilities/Dash.luau` is justified as the per-ability pattern and stays inside the "one test ability" scope. `AbilityInput` as a ModuleScript required from `init.client.luau` (in StarterPlayerScripts, so it does not reset on spawn) matches the server pattern and is justified. Both are disclosed in the implementation record.
- **Types and standards:** every new module is `--!strict`, public functions are annotated, config is frozen, pure logic lives in `*Rules`, and the service `start()` is idempotent.
