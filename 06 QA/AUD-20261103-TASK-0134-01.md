## Security and state cleanup assessment
- validLeave delegates to validJoin (JoinRules.luau:24-33): nil or empty table accepted; strings, numbers and non-empty tables rejected. No client score, Player ID, phase or other-player state is accepted.
- states[player] is selected using the engine-provided caller. Unknown/unjoined players do nothing; leaveChanges permits only already joined/participating callers.
- joined=false and participant=false are set synchronously before sendShow, with no yield. Repeats see both flags false and return without replying. This is a valid state debounce under the user's "rate-limited OR debounced" requirement; absence of a separate timer is NOT a security finding. Alternating Join/Leave is constrained by the existing JoinShow limit of four joins per ten seconds. The note's claim of sharing that limiter directly is inaccurate.
- scores() and solvers() filter participant (RoundService:70,87); SubmissionRules evaluates isParticipant and rejects post-leave answers (RoundService:277). Prior internal points remain until resetMatch, but cannot receive new credit or enter the next score list while participant=false. resetMatch clears them before next-match admission. PlayerState persists only for the connected Player as designed; PlayerRemoving removes it.
- Joining again sets joined only. Later-question participantAt preserves false, so leaving/rejoining cannot regain current-round scoring; next match resets score then admits at question 1. No mutation of other players' state or global round phase in onLeave.
- Independent Lune probe loaded an instrumented in-memory copy of the actual RoundService (no repository code edits), actual JoinRules/RateRules/SubmissionRules, with engine/services mocked.
