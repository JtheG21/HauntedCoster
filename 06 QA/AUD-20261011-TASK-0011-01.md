## Findings
| # | Severity | Location | Evidence | Required correction |
|---|---|---|---|---|
| 1 | major | `games/haunted/src/server/Services/PlayerDataService.luau:277-290`, `:160-163` | BindToClose calls `saveNow(player, true)` and decrements `pending` as soon as it returns. When a save is already in flight (a PlayerRemoving save at shutdown, or an autosave), `saveNow` just sets `queued` and returns, so `pending` hits 0 and BindToClose returns at once. The server can then close with the leave/final UpdateAsync still running. The result is lost progress since the last completed save (up to 60 s) and an unreleased lock, which delays the next join by about 30 s. This happens on every update shutdown with players online, which is exactly the case AC3 names. | In BindToClose, wait (with a 25 s deadline) until every session has `saving == false and queued == false`, or until `sessions` is empty (`onPlayerRemoving` clears entries after its save). Add a probe for it in the persistence playtest (F4). |
| 2 | major | `games/haunted/src/shared/Rules/ProfileRules.luau:136-256` (`:177`, `:180-182`, `:202-205`, `:215-217`, `:255`); spec `ProfileRules.spec.luau:82-86` | "Never-drop migration" holds only at the top level. `raw.schema` is never read, and the schema is forced to 1. Owned monsters of unknown species are deleted, unknown variants become Normal, unknown journal keys and flags are dropped, and unknown keys inside `journal` and `stats` are discarded. Each save writes the cleaned copy back. So while servers run different versions (old servers keep running after a publish), a v1 server would permanently delete a v2 player's new species, variants and flags. That contradicts AC4's "no data loss on migration". | If `raw.schema > ProfileRules.Schema`, load the profile as `readonly` (never write it) and show the banner. Optionally keep unrecognised entries in a preserved bucket rather than deleting them. Add a spec ("newer schema is not downgraded/written"). |
| 3 | minor | `PlayerDataService.luau:111-133`, `:118-123`, `:180`, `:227-230` | (a) If the player leaves after the load's UpdateAsync has taken the lock, `onPlayerAdded` returns without releasing it, and the next join waits the full 30 s. (b) Because of `lockTries < LOCK_WAIT_TRIES`, a fresh lock is stolen after 6 × 5 s = 30 s whatever `LOCK_STALE_SECONDS = 120` says, so the comment at `:6-7` overstates the protection. The old server's final save is then dropped. (c) `saveNow` writes when `rec.lock` is nil, even though this server should hold it. | Release the lock (an UpdateAsync that clears `lock` if it is still ours) when a load is abandoned. Document the 30 s steal policy, or make it match the stale threshold. Treat a missing lock as lost for a non-released session. |
| 4 | minor | Evidence ([[TEST-20261011-01]], [[TEST-20261011-02]]) | Every run used memory mode. The UpdateAsync paths, lock, retries, rejoin persistence and shutdown save have never run. For an unpublished prototype that's acceptable **only** because nothing is persisted yet. It must not count as verified. | Before any public or persistent play (a human decision to publish a private test place with Studio API access): rejoin persistence, a two-server handoff (lock wait, then load), a shutdown save with players online, and forced load failure leading to `readonly` plus the banner. Record the results as a TEST note. |
| 5 | minor | `games/haunted/src/server/Services/PlotService.luau:117` | `assign` uses `waitFor(player)` with the default 60 s timeout and isn't retried. In the worst case a load takes 30 s of lock waiting plus 2+4+8 s of backoff plus call latency, which comes close to the timeout. If it runs out, the player plays with no plot and gets no message. | Assign from `PlayerDataService.onLoaded`, or wait while `player.Parent` is set with no fixed timeout. |
| 6 | minor | `games/haunted/src/server/Services/MovementService.luau:16-24` | The speed upgrade and the 0.7× carry penalty only set `Humanoid.WalkSpeed` on a client-owned character. Nothing on the server checks movement, so an exploiter can ignore the carry slow. That doesn't fit "the server is authoritative" for the return trip, but it's acceptable for an unpublished prototype. | Track a server-side movement sanity check (displacement per second compared with the expected WalkSpeed) in an anti-exploit task before public play. |
| 7 | nit | `ProfileRules.luau:236-248` | Exhibit dedupe keys on the raw `e.slot` but stores `math.floor(e.slot)`, so `{slot=1.5}` and `{slot=1}` both end up in slot 1. | Reject non-integers (`e.slot % 1 ~= 0`) before the dedupe. |

**Fail** (0 blocker, 2 major, 4 minor, 2 nit). The scaffold, the check coverage, memory mode and the plots are sound, and the sanitizer is careful about types and ranges. The two majors are in the persistence contract the task exists to provide: BindToClose doesn't wait for serialized saves (AC3), and sanitize can destroy newer-schema data (AC4). On the untested DataStore: for an unpublished prototype I don't count the lack of a real-DataStore run as a blocker by itself (F4 is minor, tracked before publishing). The two majors are code defects that would fail even a perfect DataStore test.
