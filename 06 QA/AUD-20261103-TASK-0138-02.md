## Findings

### F1 — high: unknown stored fields are still deleted by the actual save transform
Location: games/mathshow/src/shared/ProfileRules.luau:161-162,215-216; games/mathshow/src/server/Services/ProfileService.luau:95,139-140. Spec gap: games/mathshow/tests/ProfileRules.spec.luau:207-219,257-263.

migrate clones unknown fields, but load immediately sanitizes that result into defaults plus known fields. More seriously, merge starts by sanitizing the current stored record, then returns that reduced table to UpdateAsync. Thus any unknown field is removed from persisted data. The future-version memory-only guard protects only profiles already newer at LOAD: if a future server writes a newer record after this server loaded v2, this server's save transform strips the newer fields while retaining version 99. The comment in evidence acknowledging pre-existing sanitize behaviour does not satisfy this task's explicit preservation requirement.

Executed the real ProfileRules module under Lune, no source edits: migrate({version=1,quests={a=1},flag=true,...}).flag is true; sanitize(migrate(...)).flag is nil; merge(old,{glyphsLifetime=11}) returns quests=nil and flag=nil. merge({version=99,extra="must survive",glyphsLifetime=20},{glyphsLifetime=11}) returns version=99, extra=nil. Keeping the version number alone hides this loss. Existing tests prove preservation only through migrate, not through the actual load/save composition; future merge spec asserts only the version number.

Fix: preserve unknown persisted fields while sanitizing known ones; enforce future-version safety inside the UpdateAsync transform as well as at load (cancel/refuse incompatible writes rather than erasing fields). Add specs for migrate -> load/sanitize -> merge and a newer stored version appearing after load, asserting unknown field values survive or that the write is refused. No field-deletion exemption was supplied in the audit request.

### F2 — high: max-merge loses earned lifetime increments across overlapping sessions
Location: games/mathshow/src/shared/ProfileRules.luau:230; games/mathshow/src/server/Services/ProfileService.luau:137-146. Spec gap: games/mathshow/tests/ProfileRules.spec.luau:257-263.

A lifetime counter accumulates increments; maximum of independently incremented snapshots does not. Independent executable example: both sessions load total 10; A collects common (+1), B collects rare (+5). Saving A then B through the actual merge yields 15, not 16. Reversing saves has the same result. UpdateAsync serializes the writes but cannot recover the omitted increment. ProfileService has no cross-server session lock (unchanged); its releasing table only coordinates visits within one server. The evidence at gds.txt:11 explicitly acknowledges the missing sum. A max-merge spec that only prevents decreases cannot prove no lost earned values.

Fix: persist retry-safe, exactly-once increments against the latest stored total (with stable operation identity/acknowledgement), or use an explicitly approved exclusive-session design preventing overlapping writers. Do not add schema/lock changes without jg's approval. Add a two-session interleaving spec proving total 16 and repeated UpdateAsync callbacks cannot double credit. Merely requiring old servers to stop does not protect concurrent same-version sessions.
