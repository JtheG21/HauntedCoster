- **Rebalance logic, traced by hand:**
  - **What a move does.** `rebalanceMove` returns nil once the counts are within 1. Otherwise it moves one player from the largest faction (ties go to the latest in order) to the smallest (ties go to the earliest). If max − min ≥ 2, then `from ≠ to`. Each move strictly lowers the sum of squares, so the loop converges and can't oscillate within one call.
  - **Loop bound.** The bound is `#Players:GetPlayers()`. That is enough: a single leave from a balanced state needs at most 1 move, and any imbalance needs fewer than N moves.
  - **Leaving player.** `counts(leaving)` and the candidate filter both exclude the leaving player. So this works whether or not the player is still listed in `GetPlayers()` when the handler runs (with deferred signals they may already be gone), and the leaving player is never switched.
  - **Join order.** `joinOrder` is cleaned on leave, before the loop runs. A missing entry counts as 0 (oldest).
  - **Clone removal.** When a rebalance moves a player, it fires EchoClone's new `Faction` attribute listener, which removes that player's live clone. This is intended and correct: once the player is no longer Shinobi, their clone shouldn't keep holding a plate. The side effect is that a plate held by that clone can close mid-puzzle. That is acceptable given the M2 note pointing to TASK-0006.
- **FactionRebalance scenario.** With 3 clients the start is 2/1. It picks the smallest faction (Ki) and kicks its 1 member. Without the fix the result would be `{Shinobi=2}`, and `isBalanced` returns false for 2/0, so `ok` would be false. The scenario therefore tests the `PlayerRemoving` rebalance with a real leave. The raw result in [[TEST-20261010-07]] (`after: Shinobi 1, Ki 1, ok: true`) matches the code. It only exercises the single-move path; the multi-move path is covered only by the pure spec.
- **PressurePlate.**
  - **Cost of `refreshDoor`.** It scans all tagged plates (O(P)), but only on an `Active` change or a plate removal, not every tick. That's negligible at M2 scale.
  - **Order of updates.** `SetAttribute("Active")` runs before `refreshDoor`, so the scan sees the current state.
  - **Removal handler.** It uses the cached door plus `ignore = instance`, and the `IsDescendantOf(Workspace)` guard excludes destroyed plates.
  - **Doors with no plates.** They are never touched and keep their authored state.
  - **The `plateDoors` cache.** It holds one entry per live plate. Entries are dropped on tag removal or `Destroy`, so it's bounded and not a leak.
- **[[LES-0005-Edit-Mode-Require-Cache]].** The claim (Edit-mode ModuleScript `require` caching hides spec changes) matches known Studio behaviour. The fix (run specs in a fresh Play server) is sound. Spec count 31/0 is taken from the playtest; I couldn't reproduce it.
