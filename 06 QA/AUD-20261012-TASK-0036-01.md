# Audit: TASK-0036 Persistence Load Failure (attempt 1)

## Verdict
**Pass**. No blockers or majors.

## Verified
- A live server cannot reach memory mode. `goMemory` runs only when `DEVELOPMENT_PLACE` is true (`getStore`), or when `loadFailure` returns `memory`, which needs `developmentPlace`.
- Readonly sessions never write. `saveNow` needs `saved`; `releaseLock` is only spawned for `saved` loads.
- A live `GetDataStore` failure gives `readonly` for that load; `store` stays nil and the next call retries. `saveNow` and `releaseLock` handle a nil store.
- `return if … then "memory" else "readonly", nil` returns two values and passes `--!strict`.
- Studio behaviour is unchanged. `SessionLockRules.claim/save/release` are untouched.

## Findings (all minor)
1. `DEVELOPMENT_PLACE` includes a published place playtested in Studio, so a 403 there still means memory mode, as before. This is intended but wasn't stated in the task note.
2. The specs test the pure rule only. AC2 (how `PlayerDataService` uses it, including the new `readonly` return) is evidenced by the diff and code review, not by a test.
3. Not a regression: 4 retries (2/4/8 s backoff) plus up to 30 s of lock waits can delay a live player's load before `readonly`.
4. Not a regression: if `UpdateAsync` errors after committing the lock, the readonly session never releases it; the next server waits about 30 s, then takes it over.
