## Findings
| # | Severity | Location | Evidence | Required correction |
|---|---|---|---|---|
| F1 | minor | `KiBurst.luau` `burstHandler`, `inFront(..., part.Position, ...)` | `GetPartBoundsInRadius` matches on the part's bounds, but the `inFront` range and facing test uses the part's **centre**. Example: a 30-stud-wide wall whose surface is 2 studs from the player but whose centre is more than 12 studs away is skipped. A large block whose centre sits at 90° or more to the side is also skipped. In practice, a wall can look in range and still not break. | Test the closest point on the part instead of the centre, for example `part.CFrame:PointToWorldSpace(clamp(part.CFrame:PointToObjectSpace(origin), -size/2, size/2))`. Alternatively, record a level-design constraint (wall and block size limits) in the SYS note. |
| F2 | minor | `KiBurst.luau` `pushed[part]`, `HeavyBlock.push` | The de-dupe is per part, not per assembly. `ApplyImpulse` acts on the whole assembly, so a block made of N welded parts that are all tagged gets an impulse of v·mass applied N times. That is a velocity change of N·v, which risks a fling. The current content is single-part, so this doesn't happen yet. | De-dupe by `part.AssemblyRootPart`, or document that only one part per assembly may carry the tag. |
| F3 | minor | `CrackedWall.tryBreak` | The code captures and restores `Transparency` and `CanCollide`, but `CanQuery` is always restored to `true`, not to its captured value. On restore, collision comes back with no overlap check, so a player standing in the gap can be trapped or ejected. | Capture `CanQuery` like the other two properties. Optionally, delay the restore while a character overlaps the wall (`GetPartsInPart`). |
| F4 | minor | `CrackedWall.tryBreak`, attribute `Broken` | If a wall is authored with `Broken = true`, or is left `Broken` after a hot-reload, it can never break. The 10 s respawn time was not isolated in [[TEST-20261010-06]]. | Reset `Broken` to false when walls are set up. In the playtest, time the respawn with a stopwatch or by logging `os.clock()`. |
| F5 | minor | `HeavyBlock.start`/`setup` | Setup runs only when the tag signal fires or once at start. `GetInstanceAddedSignal` fires when the tagged part enters the DataModel, so a tagged block cloned into `ServerStorage` and moved to `Workspace` later is never unanchored or given server ownership. Ownership is also only set once. If the block's assembly later changes (welds, re-anchoring), the owner can fall back to automatic, which nothing re-checks. Blocks knocked off the map are destroyed with no respawn, so the puzzle can soft-lock. | Also listen for `AncestryChanged` (or set up blocks when they are parented to Workspace). Re-assert `SetNetworkOwner(nil)` before each push if `GetNetworkOwnershipAuto()` is true. Track block respawning as a follow-up. |
| F6 | minor | [[TEST-20261010-06]] | The task's own procedure asks for a 2-client block-position comparison, a spam-activation probe, a fake-charge-value probe, and a mobile hold-to-charge check. None of these was run; the notes say "server ownership implies consistency". | Run the 2-client check and the spam and extra-argument probes before or while merging. They could be recorded in the TASK-0010-style follow-up the playtest mentions. |
| F7 | minor | `KiBurst.luau` `chargeStarts` | The charge start is not cleared when the character dies or respawns, when the faction changes, or when the KiBurst is rejected (for example while it is on its 3 s cooldown). A KiCharge from a previous life still counts if it is under 5 s old. If a re-press's KiCharge is rejected by its 0.25 s cooldown, the earlier start stays in place and the charge is overstated by up to 0.25 s. None of this lets a client exceed the real server-measured time, so it is not an exploit. It is still stale state. | Clear `chargeStarts[player]` on `CharacterAdded` or `Humanoid.Died`, and when the faction attribute changes. |
| F8 | minor | `AbilityInput.luau` End branch | `releaseId` fires on `End` even when `Begin` never reached the handler or was rejected by the server, for example when a key goes down in a TextBox and comes up after focus leaves it. A burst with no charge spends the 3 s cooldown at minimum power. Releasing while KiBurst is on cooldown also adds a server rejection and warning during normal play. A `Cancel` input sends nothing, which is fine. Touch-button hold was not tested. | Track a local `charging` flag that is set on Begin and required on End. Optionally, gate the release on the client-side cooldown so normal play doesn't produce rejection warnings. |
| F9 | nit | `AbilityConfig.KiBurst.StaleChargeSeconds = 5` | Holding R for more than 5 s gives *minimum* power, not full power. That is surprising for players, although it is documented in the config. | Decide whether the hold should stay full power, with a cap and auto-release instead of a drop to minimum. |
| F10 | nit | `KiBurst.record`, AbilityDiagnostics | The diagnostics live in `ServerStorage`, so they are not replicated, which is correct. The per-UserId attributes are never removed on `PlayerRemoving`. This is the same pattern as `AbilityService`. | Clean the attributes up on leave, or accept the pattern as it is. |
| F11 | nit | `AbilityConfig.luau` rewrite | I compared against `7e30fbd`: Dash (1.0, Q, "Dash") and EchoClone (8.0, E, "Clone") are unchanged, and each definition is still frozen. Making `keyCode` and `label` optional is handled in `AbilityInput`. Nothing is wrong here; this confirms the executor's "same values" claim. | None. |

**Scope:** The changes to `AbilityConfig`, `AbilityInput` and `init.server` were outside the task's listed files. They were needed and are declared in the Implementation record, so there is no scope creep. Server-side impulses on a server-owned unanchored part are correct. `pushDirection` is flat, so there is no vertical launch. A push of 15–45 studs/s, applied as a velocity change scaled by mass, means "heavy" has no effect on the result; that is acceptable for a spike.
